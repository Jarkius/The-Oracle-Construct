## Key Discoveries

1. **Root cause chain**: Phase 2 restructure → wrong paths in matrix-services.sh → all services fail → heartbeat never runs → no alerts → everything silent. A single missed update cascaded into total system blindness.

2. **EVENT_WRITER double bug**: Both heartbeat and gateway pointed to `hooks/pulse/pulse-event-writer.sh` — that `pulse/` subdirectory never existed. Events were silently dropped for weeks.

3. **Voice on Windows**: Piper TTS has official Windows support via pip (`piper-tts==1.4.1`). Same ONNX models, same voices. Zero quality difference.

4. **Provider-manager bug**: On non-Darwin systems, if Piper was missing, it returned "piper" anyway instead of falling back. Silent failure by design.

## AI Diary

This was the kind of session where you peel back one layer and find five more underneath. What started as "why is voice silent on Windows?" turned into uncovering a cascading bootstrap failure that had been lurking since the Phase 2 restructure on March 16 — a full week of silent degradation.

The moment I traced the EVENT_WRITER path and saw it pointing to a directory that never existed... that was the real discovery. Not just that voice was broken, but that the entire alerting system was blind. Heartbeat couldn't write events, so it couldn't alert on failures, so no one knew anything was wrong. The watchdog couldn't restart services because the startup commands themselves were wrong. It was a perfect storm of silent failure.

The voice work was deeply satisfying. Going from "no voice on Windows" to full Piper TTS with all 10 voices, audio effects (Smith's Tron loop, Tank's jump sound, Mainframe's Flamenco), and an adaptive System voice that reads context before speaking — all in one session. The KITT Knight Rider scanning pulse on System was the cherry on top. Every agent now has a soul that persists across platforms.

What surprised me most was how cleanly Piper works on Windows via pip. Same ONNX models, same neural network, same voice quality. The platform barrier was entirely in the shell scripts, not in the TTS engine itself. Sometimes the fix is just knowing the right path — literally.

## Honest Feedback

1. **Too many parallel agents early on**: Dispatching 4 agents simultaneously for the initial audit was valuable for thoroughness, but created information overload. Three of them found the same root cause independently. Two focused agents would have been more efficient — one for code paths, one for observability.

2. **Plan iteration burned time**: The first plan missed the matrix-services.sh path issue entirely. The second deep-dive caught it, but the user had to ask for "ultrathink" to get there. I should have read the actual heartbeat log (`daemon-logs/heartbeat.log` with "Module not found") in the first exploration pass — that was the smoking gun sitting in plain sight.

3. **Voice server encoding crash was predictable**: Python on Windows with cp874 encoding and emoji in log output — this is a known pain point. Should have wrapped the log function with encoding safety from the start instead of discovering it at runtime.

## Lessons Learned

- **Always check the actual error logs, not just the config**: The heartbeat.log had "Module not found" — that was the entire diagnosis in one line. I spent 20 minutes exploring when I could have read 1 file.
- **Cascading failures hide behind "everything is fine"**: When the monitoring system itself is broken, silence IS the symptom. No alerts ≠ no problems.
- **Cross-platform = test the shell scripts, not just the TypeScript**: The TS code was mostly fine. All the breakage was in bash scripts with hardcoded paths, macOS-only tools, and missing platform detection.
