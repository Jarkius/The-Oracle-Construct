## AI Diary (Required - 150+ words)

I assumed the voice system would "just work" on the new M4 since we had done portability fixes 15 days ago. I learned that portability at the script level is different from dependency portability - the scripts were portable, but Piper's binary architecture wasn't.

I was confused about why the "piper_macos_aarch64.tar.gz" release contained x86_64 binaries until I realized this is a packaging bug in the piper project. The Python piper-tts package via pipx handles this correctly by bundling the right libraries for whatever Python interpreter installs it.

I expected the fix would be simple (maybe reinstall piper) but got a multi-step journey because each fix revealed another dependency: first espeak-ng, then discovering it was ARM but piper was x86_64, then needing x86_64 Homebrew, then x86_64 Python, then x86_64 pipx.

The key insight was when the user mentioned "on M2 Pro it still can work" - this made me check for x86_64 Homebrew at `/usr/local`, which was the missing piece. The M2 Pro had both Homebrews; the new M4 only had ARM.

## Lessons Learned

- **Pattern**: On Apple Silicon, check for x86_64 dependencies when native ARM isn't available
- **Pattern**: Python packages via pipx can handle binary dependencies better than raw downloads
- **Pattern**: Always have fallback for critical systems (voice → macOS say)
- **Anti-pattern**: Don't trust release filenames (aarch64 ≠ actually ARM)
