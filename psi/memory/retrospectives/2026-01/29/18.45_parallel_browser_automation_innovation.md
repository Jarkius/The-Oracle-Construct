## Key Decisions

| Decision | Rationale |
|----------|-----------|
| AppleScript for window opening | Native macOS, true parallel, no MCP limitations |
| Puppeteer-cluster as primary recommendation | Battle-tested, CONCURRENCY_BROWSER mode, auto-cleanup |
| API mode as fastest option | No browser overhead, true parallel, instant results |
| Brave remains preferred browser | Ad-blocking, anti-detection, same Chromium engine |

## AI Diary (Required - 150+ words)

I assumed Playwright MCP could handle multiple browser windows by simply creating new tabs, but learned that MCP servers are singletons - all requests go through one browser context. This was a fundamental architectural limitation I hadn't anticipated.

I was confused about why Task agents with `run_in_background: true` weren't opening separate windows until I realized they all share the same Playwright MCP server instance. The "parallelism" was in agent execution, not browser instances.

I expected AppleScript to be unreliable for browser automation, but got surprisingly good results for window opening - it's just the keystroke targeting that proved fragile. The user's observation "I see only first windows that gemini acting" was the critical feedback that revealed AppleScript's window focus limitations.

What struck me most was the user's willingness to explore - "should we innovate our own tool?" opened a creative space. Instead of fighting Playwright's limitations, we designed three alternative approaches, each optimized for different use cases. The session transformed from troubleshooting to genuine innovation.

The research comparison (Windows vs Tabs, Browser comparison, Approach ranking) emerged from the user's rapid-fire questions. They pushed for comprehensive analysis, and that pressure produced better documentation than a single-track investigation would have.

## Lessons Learned

- **Pattern**: MCP servers are singletons - for true parallelism, use Task agents or external tools
- **Pattern**: AppleScript excels at window management, fails at keystroke targeting across windows
- **Pattern**: When a tool has fundamental limitations, design alternatives rather than workarounds
- **Pattern**: User pressure ("do more research") produces more comprehensive documentation
- **Pattern**: API calls always beat browser automation for speed when visual monitoring isn't needed
