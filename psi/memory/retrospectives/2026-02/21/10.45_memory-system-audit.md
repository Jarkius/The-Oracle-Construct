### What We Found (Evidence-Based)

**Layer 1 — Markdown (psi/)**: WORKS
- 88 session files, 71 retrospectives, 46 learnings, 18 ADRs
- Auto-saved reliably by hooks

**Layer 2 — SQLite (agents.db)**: EXISTS BUT FRAGILE
- 1.2MB database, 115 sessions, 119 learnings
- `bun memory recall --last` works (SQLite-only path)
- `bun memory status` works
- BUT: Stop hook is `async: true` → SQLite save races against exit
- BUT: All errors masked by `2>/dev/null || true`

**Layer 3 — ChromaDB**: DEAD
- Docker daemon not running in this environment
- `docker ps` → "failed to connect to the docker API"
- Every `bun memory recall "query"` crashes with `ChromaConnectionError`
- No fallback to FTS-only search

**Learnings Quality**: GARBAGE
- All 119 entries: `"*Auto-captured by session-memory-save hook*"`
- All category: "performance" (wrong — should be varied)
- All confidence: "low" (correct — they ARE low quality)
- Zero link to tasks, missions, or code files

**Recall Pipeline**: CRASHES
- `recall-service.ts:631` — `await initVectorDB()` with no try/catch
- When ChromaDB is down, function throws instead of falling back to `searchLearningsFTS()`
- FTS function exists (line 318) but is only called inside the vector path
- Result: the system has FTS but can't reach it when ChromaDB is down

## AI Diary

I assumed the memory system worked because the code existed and `bun memory status` showed numbers — 115 sessions, 119 learnings. But I learned that quantity without quality is worse than nothing. Every one of those 119 learnings says the same thing: "Auto-captured by session-memory-save hook." That's not a learning. That's a timestamp pretending to be knowledge.

I was confused about why `bun memory recall "query"` crashed until I read the actual code. Line 631 of recall-service.ts calls `await initVectorDB()` with no error handling. When ChromaDB is down, it throws `ChromaConnectionError` and the function dies. There's a perfectly good `searchLearningsFTS()` function at line 318 — it uses SQLite full-text search, which works fine without ChromaDB. But the code never reaches it because the vector initialization crashes first. The fallback exists but is unreachable.

I expected the async Stop hook to be a minor issue. But it's actually the core reliability problem. The Stop hook in `.claude/settings.json` line 44 has `"async": true`. This means the session ends immediately and `pulse-session-end.sh` runs in the background. If `bun memory save` takes more than a second or fails, nobody knows. All three bun calls use `2>/dev/null || true` — errors are invisible. The markdown save works because it's fast (just file write). The SQLite save is slower and may or may not complete before the process dies. We have no way to know how many sessions were actually persisted to SQLite vs just markdown.

The hardest realization: the operator's instinct was right. "If we still forget, how could we do real projects?" We can't. The memory system looks complete from the outside — 17 phases, semantic search, dual-layer persistence. But it's a filing cabinet with no librarian. Files go in, nothing comes back out when you need it.

## Lessons Learned

- **Pattern**: Error masking (`2>/dev/null || true`) creates invisible failures. Log errors, don't hide them. (Confidence: proven)
- **Pattern**: Async hooks for critical persistence are a design error. Data that MUST be saved should block exit. (Confidence: high)
- **Pattern**: Building for environments you don't have (ChromaDB/Docker) creates dead code. Always have a working fallback. (Confidence: high)
- **Pattern**: Quantity of stored records means nothing without quality. 119 identical "auto-captured" entries = 0 learnings. (Confidence: proven)
