# Session Retrospective: The Memory System Actually Works Now

**Date**: 2026-02-21 09:30–11:00 UTC
**Duration**: ~90 minutes
**Focus**: Audit and fix the memory system — from theater to function

## Summary

Session started with the operator reviewing all pending plans across 17 infrastructure phases. The honest question — "why lots of code but not efficient, not effective, not proactive?" — triggered a deep audit of the memory system. Found 3 critical bugs: recall crashes without ChromaDB (no try/catch), stop hook loses data silently (async + error masking), and 117 garbage learnings polluting search. All 3 fixed in 30 minutes. Memory system now returns real results via FTS when ChromaDB is unavailable, saves reliably to SQLite on every session end, and contains 83 real learnings + 71 retrospective sessions instead of garbage.

## What We Built

### Fix 1: Recall Fallback (recall-service.ts)
- Wrapped `initVectorDB()` in try/catch — falls back to FTS-only mode
- `hybridSearchLearnings()` catches vector search failure, returns keyword results only
- `recallBySearch()` skips vector session/task search when ChromaDB is down
- Dynamic weight adjustment: 36%/64% vector/FTS when both available, 0%/100% FTS-only

### Fix 2: Stop Hook Reliability (settings.json + pulse-session-end.sh)
- Changed Stop hook from `async: true` to `timeout: 15000` — synchronous with 15s limit
- Replaced `2>/dev/null || true` with `2>>"$MEMORY_LOG"` — errors logged to `psi/pulse/memory-errors.log`
- Removed broken `bun memory distill` call that produced garbage

### Fix 3: Purge + Backfill (backfill-from-psi.ts)
- Deleted 117 garbage "Auto-captured" learnings from SQLite
- Created `backfill-from-psi.ts` — imports psi/ markdown directly to SQLite (no ChromaDB needed)
- Imported: 71 retrospective sessions, 46 learnings, 18 ADRs, 5 blueprints/plans, 14 active research
- Total: 83 real learnings, all FTS-indexed via SQLite triggers

## Key Decisions

| Decision | Rationale |
|----------|-----------|
| Fix memory before CIS | Can't build real projects if sessions forget everything |
| Accept ChromaDB unavailable in sandbox | Docker not available — FTS fallback is sufficient |
| Remove distill from stop hook | Produced 117 identical garbage entries — worse than nothing |
| Sync stop hook (remove async) | Data that must persist should block exit |
| Log errors instead of masking | `2>/dev/null || true` made failures invisible |
| Backfill via direct SQLite, not `bun memory learn` | `learn` calls ChromaDB which crashes — direct insert bypasses it |

## AI Diary

I assumed the memory system was fundamentally sound because the code existed — 17 phases, 872 lines in recall-service.ts, dual-layer persistence in the ADR. I learned that code existing and code working are completely different things. One missing try/catch block (line 631 of recall-service.ts) made the entire recall system crash. One `async: true` flag in settings.json made session persistence unreliable. One broken distill call created 117 garbage entries that polluted every search.

I was confused about why the operator felt the system "wasn't proactive" until I tested it myself. `bun memory recall "authentication MD5"` — crash. `bun memory recall "CIS modernization"` — crash. The mandatory recall protocol in CLAUDE.md said "search before you speak" but the search literally could not execute. The protocol was performative, not functional.

I expected the fixes to be complex — maybe requiring ChromaDB configuration, embedding model tuning, or major refactoring. But the actual fixes were surgical: one try/catch, one flag change, one SQL DELETE, one backfill script. Total real code changes: ~60 lines in recall-service.ts, 2 characters in settings.json (`async: true` → `timeout: 15000`), 15 lines in pulse-session-end.sh. The backfill script was 275 lines but that's a one-time utility.

The moment that mattered: running `bun memory recall "authentication MD5"` after the fix and seeing 7 real results — Legacy Authentication Logic, tech stack justification, migration research. Not a crash. Not garbage. Real knowledge, searchable by keyword, linked to source files. That's what the system was supposed to do from day one.

The operator asked "if we still forget, how could we do real projects?" The answer was: we couldn't. Now we can. FTS isn't as powerful as semantic vector search, but it's infinitely better than a crash.

## Lessons Learned

- **Pattern**: Error masking (`2>/dev/null || true`) is technical debt that compounds silently. Always log errors, even in hooks. (Confidence: proven — 117 garbage entries accumulated undetected)
- **Pattern**: Async hooks for critical persistence are a design error. If data must survive, block until it's saved. (Confidence: proven — sync hook now works reliably)
- **Pattern**: Test the full user path, not just unit tests. `bun memory status` passed but `bun memory recall "query"` crashed. Status ≠ function. (Confidence: high)
- **Pattern**: When infrastructure doesn't serve the mission, fix the infrastructure — don't build more of it. (Confidence: proven — this session)
- **Pattern**: Backfill scripts are valuable. Real markdown data existed in psi/ but wasn't in SQLite. One script bridged the gap. Keep `backfill-from-psi.ts` for future data migrations. (Confidence: high)
